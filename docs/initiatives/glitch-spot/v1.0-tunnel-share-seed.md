## 1. Stage at a glance

**Name:** `v1.0-tunnel-share`

**Goal:** Let a developer share an annotated Glitch Spot snapshot with a teammate by exposing the existing local server over a tunnel (ngrok, Tailscale Funnel, cloudflared, or similar). The snapshot stays on the developer's machine; only the URL travels.

**Why this and not a cloud relay?** The original v1.0 stage called for Cloudflare Workers + R2. We're deferring that because:

- Tunnels give us cross-machine sharing without standing up backend infrastructure
- Snapshots that already persist locally (v0.3) can be served as-is — no double upload
- The cost and complexity of running a hosted service isn't justified for the team-internal use case
- If the tunnel approach proves insufficient later (durable public links, web-host DOM enrichment, etc.), the cloud relay is preserved as a `later:` stage in INITIATIVE.md

**Non-goals (do not in-scope these):**

- Cloudflare Workers / R2 / any cloud-hosted relay
- The `@glitch-spot/web` SDK for DOM-path enrichment
- Durable public links (TTL beyond app/session lifetime)
- Team-level auth, accounts, or permissions
- Windows or Linux ports

## 2. Project orientation (5-minute version for a fresh agent)

Glitch Spot is a Tauri 2 macOS dev-time annotation tool. Press `Ctrl+Opt+Cmd+G` (or `H` for frozen mode), a transparent overlay captures the screen, you drag rectangles and add notes, press `Cmd+Return`, and a JSON snapshot lands on the clipboard plus an annotated PNG. It runs as a menu-bar app (no Dock icon).

Shipped stages relevant to this work:

- **v0.2-drawing** — overlay, drawing, snapshot JSON on clipboard, annotated PNG generation
- **v0.3-persistence** — snapshots persist to `~/.glitch-spot/snapshots/{id}/{clean.png, annotated.png, snapshot.json}`; mtime-based 24h sweep at app startup
- **v0.4-mcp** — local axum HTTP server on `127.0.0.1:7820` exposing MCP JSON-RPC tools (`wait_for_snapshot`, `get_latest_snapshot`, `get_snapshot(id)`, `cancel_wait`) for AI-agent integration; menu-bar tray with autostart + dynamic snapshot-age label

This stage builds directly on v0.4 (the server) and v0.3 (the on-disk snapshot files).

For full project background: [`scope.md`](./scope.md) (note: the v1 framing in that doc is partially superseded — it described a Cloudflare relay; the current direction is this stage instead).

## 3. Approach hint (not a decision — a starting frame)

The cheapest design that meets the goal:

1. Extend the existing axum server (`src-tauri/src/mcp/server.rs`) with read-only routes under a new path prefix. Something like:
   - `GET /share/{id}/snapshot.json` → reads from `~/.glitch-spot/snapshots/{id}/snapshot.json`
   - `GET /share/{id}/clean.png` → reads `~/.glitch-spot/snapshots/{id}/clean.png`
   - `GET /share/{id}/annotated.png` → reads `~/.glitch-spot/snapshots/{id}/annotated.png`
   - (Optionally) `GET /share/{id}` → an HTML view rendering the annotated image + notes for human consumption
2. Spawn or connect to a tunnel process (ngrok / Tailscale Funnel / cloudflared) that exposes `127.0.0.1:7820` publicly. Capture the public URL.
3. Surface the per-snapshot share URL (`{public-url}/share/{id}`) to the user — clipboard on save? Tray menu action? Both?

The brainstorm should pressure-test this frame, not accept it uncritically.

## 4. Decided constraints (do not re-argue)

- **Tauri 2, macOS only.** Windows + Linux are deferred indefinitely (see `future-ports` in INITIATIVE.md).
- **No new cloud infrastructure.** No Workers, no R2, no managed service.
- **The snapshot data model is fixed.** Schema lives in `src-tauri/src/snapshot/mod.rs`. The on-disk layout (`~/.glitch-spot/snapshots/{id}/{clean.png, annotated.png, snapshot.json}`) is v0.3's stable contract. Don't change either.
- **The 24h startup cleanup is live.** Any snapshot older than 24h is swept on app launch. The design must reconcile share-link lifetime with this — either accept that shared links go dead after 24h, or extend retention for shared snapshots.
- **The MCP server lives on `127.0.0.1:7820`.** Any new share routes must coexist on that server without breaking MCP's `POST /mcp` route.

## 5. Open design questions (drive the brainstorm)

1. **Which tunnel provider(s) to support?**
   - **ngrok** — easiest UX (single binary, one-click URL); requires a user-level ngrok account and authtoken; has a free tier with random subdomains and rate limits
   - **Tailscale Funnel** — zero third-party for users already on Tailscale; the URL is `*.ts.net` and only reachable from outside Tailscale if Funnel is enabled; assumes both sender and recipient can resolve
   - **cloudflared (Cloudflare Tunnel)** — free, no account needed for ephemeral URLs (`trycloudflare.com`); URLs are random and short-lived
   - **localtunnel / others** — generally less reliable
   - Single provider, picked at build time? User-selectable in settings? Auto-detect what's installed?

2. **Tunnel process lifecycle.**
   - Desktop app spawns the tunnel binary as a child process at startup / on first share?
   - Or the user runs the tunnel externally and pastes the URL into a settings field?
   - First gives a one-click UX; second is simpler to ship and works with any tunnel.

3. **Auth model.**
   - None — the URL itself is the secret (`/share/{snap_id}` where the id is a random 12-char suffix)
   - Path-embedded random token separate from the snapshot id
   - Optional passcode the user shares out-of-band (matches scope.md §10's relay design)
   - Restrict by IP / referrer / origin?

4. **Share lifetime.**
   - URL is valid while the app is running and stops on quit?
   - URL is valid until the snapshot is cleaned up (24h)?
   - Configurable per-share TTL?
   - The persistence model (URL stops working when the app quits vs survives restarts) directly affects the UX promise to teammates.

5. **UX entry point — how does the user get a share URL?**
   - Auto-share on save: every `Cmd+Return` finalisation puts both the JSON and a share URL on the clipboard
   - Explicit "Share…" tray action against the latest snapshot
   - Per-snapshot "Share…" submenu (against the latest N snapshots)
   - Hotkey for "share last snapshot"?
   - Each option implies different mental models for the user.

6. **JSON-only or HTML view?**
   - scope.md §10 described an HTML view for human teammates rendering the annotated image + notes. Should v1.0-tunnel-share include this, or stay JSON+images-only and defer the HTML to a later stage?
   - The HTML view is small (one server-rendered page); the question is scope discipline.

7. **Error handling / failure modes.**
   - Tunnel binary not installed
   - Tunnel auth failure (ngrok authtoken missing / Tailscale Funnel disabled)
   - Tunnel started but disconnects mid-share
   - Local server not reachable from the tunnel (firewall, port conflict)
   - What does the tray show? What does the clipboard contain on failure?

8. **Security posture.**
   - A tunnel exposes `127.0.0.1:7820` to the public internet. The MCP routes (`/mcp`) currently assume localhost-only trust. We MUST scope the tunnel to the `/share/*` routes only (or split the MCP server into a separate localhost-only listener), otherwise we'd expose the MCP control surface publicly.
   - This is the most important security question; it's load-bearing on the architecture.

9. **Multi-monitor / multi-display.**
   - Currently outside v0.3 — each snapshot is a single monitor capture. No change here, but worth confirming the share URL pattern still works if/when multi-monitor lands.

## 6. Pointers to existing code

| Path | Why it matters |
|---|---|
| `src-tauri/src/mcp/server.rs` | The existing axum server. `build_router(store)` is where to extend with `/share/*` routes. Currently registers `POST /mcp` and exposes a `serve(store)` function that binds `127.0.0.1:7820`. |
| `src-tauri/src/mcp/store.rs` | In-memory `SnapshotStore` that MCP reads from. Not directly relevant for `/share/*` (which reads from disk), but useful for understanding the existing server's state model. |
| `src-tauri/src/snapshot/persist.rs` | Disk-backed snapshots — `snapshots_dir()` resolves `~/.glitch-spot/snapshots/`, `write()` materialises a `BuiltSnapshot`, `cleanup(base, max_age)` is the 24h sweep. `/share/*` routes will read files from `snapshots_dir().join(id)`. |
| `src-tauri/src/snapshot/mod.rs` | The `Snapshot` schema (id, created_at, mode, annotations, context, images). Don't modify; serve as-is. |
| `src-tauri/src/snapshot/build.rs` | Pure `build()` returning `BuiltSnapshot`. Not directly modified by this stage. |
| `src-tauri/src/tray.rs` | Menu-bar setup. A "Share…" action would land here. The `build_menu` function is called on every tray click — extend it with new items. |
| `src-tauri/src/lib.rs` | `pub fn run()` orchestrates everything (MCP server spawn, startup cleanup, Tauri Builder). Also hosts `save_snapshot` — if the share URL goes on the clipboard, that's where to wire it. |
| `src-tauri/src/bin/mcp_server.rs` | Standalone binary that reuses `build_router`. Useful precedent for "extend `build_router` with extra routes" — see how it merges its own `/test/inject` route. |
| `docs/initiatives/glitch-spot/scope.md` | Original v1 design. Useful for snapshot schema (§6), MCP contract (§9), and relay design (§10) — but the relay framing is now superseded by this stage. |
| `docs/initiatives/glitch-spot/INITIATIVE.md` | Source of truth for current roadmap and stage state. |

## 7. Working agreements (Glitch Spot conventions)

These are non-negotiable; Dmitry's CLAUDE.md enforces them:

- **Branch:** create `v1.0-tunnel-share` for the implementation work. NEVER commit to `main` directly.
- **Worktree:** use `superpowers:using-git-worktrees` (or the `EnterWorktree` tool) before implementation work; the project's worktree dir is `.claude/worktrees/`.
- **TDD:** every new feature or bugfix gets a failing test first, then minimal implementation, then refactor.
- **YAGNI:** ship the smallest thing that meets the goal. Don't speculatively add features.
- **Workflow:**
  1. `superpowers:brainstorming` → produce a refined design seed in this file (overwriting this handoff)
  2. `superpowers:writing-plans` → produce `docs/plans/YYYY-MM-DD-v1.0-tunnel-share.md`
  3. `superpowers:using-git-worktrees` → create worktree
  4. `superpowers:subagent-driven-development` → fresh subagent per task, two-stage review
- **Model selection for subagents:** implementer → sonnet, reviewers → opus, final reviewer → opus (Dmitry's CLAUDE.md spells this out — read it).
- **Commit messages:** imperative, focused, no emojis, no banners/badges/tool attribution.
- **`cargo` not on default PATH:** prepend `$HOME/.cargo/bin` for cargo invocations (`PATH=$HOME/.cargo/bin:$PATH cargo test`). Pass this to subagents in their prompts.
- **Comments:** ABOUTME headers on every code file (two `// ABOUTME: ` lines). No "what used to be here" comments.
- **Ask, don't assume.** When the design is ambiguous, stop and ask Dmitry. Especially before architectural decisions.

## 8. What "done" looks like for this stage

- Sharing a snapshot is a one-click action from either the tray menu or save flow (final UX TBD in brainstorm)
- The share URL works from another machine on the internet (or another Tailnet device, depending on tunnel choice)
- The MCP routes (`/mcp`) are NOT exposed via the tunnel — only `/share/*`
- Tests cover: route serves correct content for a known snapshot id, route 404s for missing id, route is rejected (or omitted) if the tunnel front of the server tries to call `/mcp`
- INITIATIVE.md ticks `v1.0-tunnel-share` `[x]`, plan moves to `docs/plans/completed/`, branch merges to main
- A manual smoke test confirms a real share URL is reachable from a phone (or another machine) and renders the annotated image
