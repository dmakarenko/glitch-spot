**Date:** 2026-05-26
**Status:** Design settled; implementation plan to follow
**Part of initiative:** [`INITIATIVE.md`](./INITIATIVE.md)
**Supersedes:** the pre-brainstorm handoff (same filename, commit `9be58b4`)

---

## 1. Stage at a glance

**Name:** `v1.0-tunnel-share`

**Goal:** Let a developer share an annotated Glitch Spot snapshot with a teammate by exposing a tunneled local HTTP server. The snapshot stays on the developer's machine; only the URL travels. The teammate opens the link and sees the annotated screen plus notes in their browser.

**One-line architecture:** A second axum listener on `127.0.0.1:7821` serves read-only `/share/{id}/{token}/...` routes from disk; on first "Share latest…" click, the app spawns a user-configured tunnel binary (cloudflared / ngrok / Tailscale Funnel) pointing at 7821 and captures the public URL.

**Non-goals (explicitly out of scope):**
- Cloudflare Workers / R2 / any cloud-hosted relay (preserved as a `later:` stage in INITIATIVE.md)
- `@glitch-spot/web` SDK for DOM-path enrichment
- Durable public links across app restarts
- Team-level auth, accounts, or permissions
- Per-share TTLs, share revocation, browseable share lists
- Windows or Linux ports

## 2. Architecture

### 2.1 Two-listener topology

```
glitch-spot process
├── MCP server      127.0.0.1:7820   POST /mcp                  (unchanged from v0.4)
└── Share server    127.0.0.1:7821   GET  /share/{id}/{token}/* (NEW; only this port is tunnelled)
                                     GET  /healthz
```

Both listeners spawn in `lib.rs::run()` at app startup. The share router has **zero** MCP routes — even if the tunnel binary were misconfigured, `/mcp` does not exist on `7821`.

### 2.2 Share routes (read-only, on 7821)

```
GET /share/{id}/{token}/              → HTML view (annotated PNG + numbered notes list + "Raw JSON" link)
GET /share/{id}/{token}/snapshot.json → application/json, from ~/.glitch-spot/snapshots/{id}/snapshot.json
GET /share/{id}/{token}/clean.png     → image/png,        from .../{id}/clean.png
GET /share/{id}/{token}/annotated.png → image/png,        from .../{id}/annotated.png
GET /healthz                          → 200 "ok"
```

All four `/share/*` routes:

1. Resolve `{id}` to `~/.glitch-spot/snapshots/{id}/` via `snapshot::persist::snapshots_dir()`.
2. Read the per-snapshot `share-token` file. Missing → 404 (snapshot was never shared).
3. Constant-time compare against `{token}`. Mismatch → 404 (deliberately not 401 — never signal the id exists).
4. Serve the requested file. 404 if the underlying file is missing on disk.

The HTML handler renders a single Rust-`format!`-built page: `<img src="annotated.png">` at top, `<ol>` of `annotation.note` values matching rectangle order (numbered to match the in-image labels), footer "Open raw JSON" link to the JSON sibling. No JS, no templating engine, no external CSS.

### 2.3 Auth model

- **The URL itself is the secret.** No HTTP auth, no passcode UI.
- **Per-share token:** 128 bits of cryptographic randomness (`rand::rngs::OsRng` → `[u8; 16]` → base64url, 22 chars). The `rand` crate's `OsRng` is suitable.
- **Persisted as:** `~/.glitch-spot/snapshots/{id}/share-token` (file mode `0600`, text body is just the token string with a trailing newline).
- **A snapshot only becomes shareable** after the user explicitly clicks "Share latest…" — until then, no token file exists and `/share/{id}/...` returns 404 regardless of the URL guessed.
- **Token verification is constant-time** (`subtle::ConstantTimeEq` or equivalent).
- **Re-sharing the same snapshot:** clicking "Share latest…" on a snapshot that already has a `share-token` file overwrites it with a fresh token. The previous URL stops working — the only durable share URL is the one currently on the clipboard.

### 2.4 Share lifetime

- Bound to the app session that created the share.
- Quit Glitch Spot → tunnel child process is SIGTERM'd → public URL stops resolving.
- The on-disk `share-token` file persists until the existing 24h sweep deletes the snapshot dir; without a live tunnel, it's harmless (no public route reaches it).
- If the app starts a new session, a fresh tunnel URL is generated and old share URLs (which embed the old tunnel host) are dead.
- We do NOT proactively delete `share-token` files on shutdown — the 24h sweep already handles cleanup.

### 2.5 Multi-monitor (forward-looking)

The share routes serve per-snapshot files from disk. When multi-monitor capture lands (deferred), each capture still produces one snapshot per id with its own directory — `/share/{id}/{token}/...` keeps working unchanged. No schema change in this stage.

## 3. New module layout

```
src-tauri/src/share/
├── mod.rs               // re-exports; ABOUTME
├── router.rs            // build_share_router(state) → axum::Router
├── html.rs              // render_share_page(snapshot) → String
├── token.rs             // generate(), write_for(id), read_for(id), verify_constant_time()
└── tunnel/
    ├── mod.rs           // TunnelManager state machine + child-process owner
    ├── provider.rs      // trait TunnelProvider; enum ProviderKind
    ├── cloudflared.rs   // adapter
    ├── ngrok.rs         // adapter
    └── tailscale.rs     // adapter

src-tauri/src/settings.rs   // ConfigFile load/save for ~/.glitch-spot/config.toml
src-tauri/src/tray.rs       // EXTENDED: tunnel-status label + provider submenu + "Share latest…"
src-tauri/src/lib.rs        // EXTENDED: spawn share listener; wire TunnelManager into AppHandle state;
                            //            SIGTERM tunnel on RunEvent::ExitRequested
```

### 3.1 `share::tunnel::TunnelManager`

`Arc<Mutex<TunnelManagerInner>>` central store (same pattern as the existing `SnapshotStore`). Owns:

- The current `ProviderKind` (loaded from settings on each `share_latest` call, so changing the provider in the tray takes effect on next share).
- The current `tokio::process::Child` (if any) plus a join handle for its stderr-reader task.
- The current public URL (when `Live`).
- The current `TunnelState`:
  - `Idle` — no tunnel running
  - `Starting` — spawn issued, awaiting URL
  - `Live { url: String }` — URL captured
  - `Error { reason: String }` — last attempt failed; retry on next `share_latest`
- A `tokio::sync::watch::Sender<TunnelState>` so the tray re-renders on transitions.

**Public API:**

```rust
impl TunnelManager {
    pub fn new(settings: Arc<Settings>) -> Self;
    pub async fn share_latest(&self, snapshot_id: &str) -> Result<String, ShareError>;
    pub fn current_state(&self) -> TunnelState;
    pub fn subscribe(&self) -> watch::Receiver<TunnelState>;
    pub async fn shutdown(&self);
}
```

### 3.2 `share::tunnel::TunnelProvider` (trait + adapters)

```rust
#[async_trait]
pub trait TunnelProvider: Send + Sync {
    /// Spawn the tunnel binary pointing at local_port. Returns the child process
    /// and a future resolving to the public URL (or an error) once it appears.
    async fn spawn(
        &self,
        local_port: u16,
    ) -> Result<(Child, BoxFuture<'static, Result<String, String>>), ProviderError>;
    fn kind(&self) -> ProviderKind;
}
```

Per-provider implementation notes:

- **cloudflared:** `cloudflared tunnel --url http://127.0.0.1:7821`. URL discovered by regex `https://[a-z0-9-]+\.trycloudflare\.com` against stderr lines (cloudflared writes the trycloudflare URL to stderr early in startup).
- **ngrok:** `ngrok http 7821 --log=stdout --log-format=json`. After spawn, poll `http://127.0.0.1:4040/api/tunnels` until `tunnels[0].public_url` appears (or the 10s deadline elapses).
- **tailscale:** `tailscale funnel --bg 7821`. URL = `https://<Self.DNSName>` from `tailscale status --json`. If the device doesn't have Funnel capability, the `tailscale funnel` exit code surfaces the reason verbatim.

Each adapter has a **10-second deadline** to emit a URL. Missing the deadline → `Error { reason: "<provider> failed to publish a URL within 10s" }`.

## 4. End-to-end data flow

### 4.1 "Share latest snapshot" click

1. User clicks tray → "Share latest snapshot…" (disabled and grayed out when zero snapshots exist, or when state is `Starting`).
2. Tray handler calls `TunnelManager::share_latest(latest_id)`:
   1. Acquire state lock.
   2. **`Idle` or `Error`:** read `ProviderKind` from settings, transition to `Starting`, broadcast on the watch channel (so tray updates), spawn the adapter, race its URL future against a 10s timeout. On success → `Live { url }`. On failure → `Error { reason }`, fire macOS notification, return `Err(ShareError::TunnelStartFailed)`.
   3. **`Starting`:** unreachable from the UI (menu is disabled); defensive `Err(ShareError::Busy)`.
   4. **`Live { url }`:** continue with the cached URL.
3. Generate a fresh token (`share::token::generate()`), write `~/.glitch-spot/snapshots/{id}/share-token` (mode `0600`).
4. Build the URL: `{tunnel_url}/share/{id}/{token}/` (trailing slash → HTML view).
5. Write to clipboard via Tauri's clipboard plugin.
6. Fire macOS notification: title "Glitch Spot", body "Share URL copied to clipboard".
7. Tray re-renders to show `Tunnel: <url>` status line.

### 4.2 App quit

On `RunEvent::ExitRequested`:

1. Call `TunnelManager::shutdown()`.
2. SIGTERM the child process; wait up to 2 s; if still alive, SIGKILL.
3. Proceed with normal Tauri shutdown.

### 4.3 Tunnel disconnect mid-session

The stderr-reader task also watches for child exit. If the child exits while state is `Live`:

1. Transition to `Error { reason: "tunnel disconnected" }`.
2. Broadcast on the watch channel; tray updates.
3. Fire macOS notification.
4. Previously-shared URLs are silently dead. Next `share_latest` call will respawn the tunnel (which may produce a different URL for cloudflared quick-tunnel; accepted per §2.4).

## 5. Settings & UI

### 5.1 Config file

Location: `~/.glitch-spot/config.toml`.

```toml
[tunnel]
provider = "cloudflared"   # one of: "cloudflared", "ngrok", "tailscale"
```

Created lazily on first write (when the user changes the provider in the tray). On read, missing file or missing `[tunnel].provider` → default to `"cloudflared"`. If `cloudflared` is also not on PATH at share time, the share attempt produces a clear `Error { reason: "cloudflared not installed" }`.

### 5.2 Tray UI

```
Glitch Spot
─────────────────────────
Snapshot age: 3m ago         ← existing
─────────────────────────
Share latest snapshot…       ← NEW (disabled if no snapshots; disabled if state == Starting)
Tunnel: <state>              ← NEW status line, one of:
                                  "idle"
                                  "starting…"
                                  "<short url>"      (e.g. "abc-def-123.trycloudflare.com")
                                  "error — <reason>"
Tunnel provider           ▸  ← NEW submenu (radio):
   ⦿ cloudflared
   ◯ ngrok
   ◯ Tailscale Funnel
─────────────────────────
Open snapshots folder        ← existing
Quit                         ← existing
```

Changing the provider while `Live`: SIGTERM the current child, transition to `Idle`. Do **not** auto-respawn — the user will trigger the next share themselves.

The status line displays a shortened URL (host only) when `Live`, since the full `https://.../share/{id}/{token}/` is too long for a tray label. The full URL goes on the clipboard.

## 6. Error handling

All tunnel failures surface via two channels:
1. The `Tunnel: …` tray status line (always visible when the tray is open).
2. A one-shot macOS notification on the transition into `Error`.

Specific cases:

| Cause | Tray status | Notification body | Clipboard? |
|---|---|---|---|
| Binary not on PATH | `error — <provider> not installed` | `Install <provider> or pick another in Settings.` | untouched |
| ngrok authtoken missing | `error — ngrok authtoken missing` | `Run "ngrok config add-authtoken <token>" once, then retry.` | untouched |
| Tailscale Funnel disabled | `error — Funnel disabled` | `tailscale funnel` stderr, verbatim. | untouched |
| URL not published within 10 s | `error — <provider> didn't publish a URL` | `Check ~/.glitch-spot/tunnel.log for details.` | untouched |
| Port `7821` already bound | App-startup `eprintln!`; share routes never come up | n/a (handled by listener) | n/a |
| Child exits while Live | `error — tunnel disconnected` | `Tunnel process exited. Open the tray to retry.` | untouched (any previously-shared URL is now dead — accepted per §2.4) |
| Token mismatch | n/a (route returns 404) | n/a | n/a |
| Snapshot file missing post-cleanup | n/a (route returns 404) | n/a | n/a |

All tunnel-binary stdout and stderr are tee'd to `~/.glitch-spot/tunnel.log` (append-only; no rotation — YAGNI for v1.0).

## 7. Testing approach

### 7.1 Unit tests

- **`share::token`**: `generate()` returns 22 chars from the base64url alphabet; `verify_constant_time()` accepts a matching token and rejects a same-length non-match; missing file → `None`; round-trip `write_for` then `read_for` returns the same token; mode bits on the file are `0o600`.
- **`share::router`**: assemble a Router over a temp directory, exercise:
  - 200 + correct body for `/share/{id}/{token}/snapshot.json`
  - 200 + `image/png` content-type for `/clean.png` and `/annotated.png`
  - 200 + HTML body for `/share/{id}/{token}/` (assert: `<img src="annotated.png">` present; ordered list of notes present in correct order; "Open raw JSON" link present)
  - 404 for unknown id
  - 404 for snapshot dir without a `share-token` file
  - 404 for wrong token (even if id is real and snapshot has a token)
  - 404 for valid token but missing file on disk (simulates post-cleanup race)
  - 200 "ok" for `/healthz`
- **`share::html::render_share_page`**: golden-string subset assertion (annotations render in order; JSON link present).

### 7.2 Integration tests

- **`MockTunnelProvider`** (test-only) implementing `TunnelProvider`. Returns a stub `Child` (a `tokio::process::Command::new("sleep")` or similar) and an immediately-resolved URL future. Lets us drive `TunnelManager` state transitions without spawning a real binary:
  - `Idle → Starting → Live` on `share_latest`
  - Second `share_latest` while `Live` short-circuits (no second spawn)
  - `Idle → Starting → Error` when the mock URL future returns an error
  - `Live → Idle` on `shutdown`
- **End-to-end (extends v0.3 pattern):** write a real snapshot via `persist::write`, call `TunnelManager::share_latest` with the mock provider, then hit the share Router via `tower::ServiceExt::oneshot` with the resulting URL path, assert the HTML view comes back with the right note text.

### 7.3 Manual smoke test (release gate)

1. `brew install cloudflared` (assumed present in dev env).
2. Launch Glitch Spot.
3. Capture a snapshot with one annotation.
4. Tray → "Share latest snapshot…". Confirm:
   - Clipboard contains the share URL.
   - Tray status shows `Tunnel: abc-xyz.trycloudflare.com` (or similar).
   - macOS notification fires.
5. Open the URL on a phone (or another machine off the LAN). Confirm annotated image renders and the note appears below.
6. Quit Glitch Spot; refresh the page on the phone; confirm the URL is now dead.

## 8. Decided constraints (carried forward; do not re-argue)

- **Tauri 2, macOS only.** Windows + Linux remain deferred.
- **No new cloud infrastructure.** No Workers, no R2.
- **Snapshot data model is fixed.** Schema in `src-tauri/src/snapshot/mod.rs`. On-disk layout `~/.glitch-spot/snapshots/{id}/{clean.png, annotated.png, snapshot.json}` is unchanged.
- **24h startup cleanup is live.** `share-token` files are deleted with the rest of the snapshot dir when the snapshot ages out. Shared snapshots do not get extended retention.
- **MCP server stays on `127.0.0.1:7820`.** Share server is a **separate** listener on `127.0.0.1:7821`.

## 11. What "done" looks like

- Tray menu has a **"Share latest snapshot…"** item that:
  - Is disabled when zero snapshots exist.
  - On click: spawns the configured tunnel (if not running), generates a fresh token, writes it to `~/.glitch-spot/snapshots/{id}/share-token`, copies the share URL to the clipboard, fires a macOS notification.
- Tray status line shows the current `Tunnel: idle / starting… / <host> / error — <reason>`.
- Tray provider submenu lets the user pick `cloudflared` / `ngrok` / `Tailscale Funnel`; selection persists to `~/.glitch-spot/config.toml`.
- `127.0.0.1:7821` serves `/share/{id}/{token}/...` routes correctly per §2.2 and the error matrix in §6.
- `127.0.0.1:7820` (MCP) is **not** reachable through the tunnel — verified by an integration test asserting the share Router has no `/mcp` route.
- Unit + integration tests per §7 pass under `PATH=$HOME/.cargo/bin:$PATH cargo test`.
- Manual smoke test (§7.3) passes against a real cloudflared tunnel on at least one off-LAN device.
- `INITIATIVE.md` ticks `v1.0-tunnel-share` `[x]` with the PR ref; plan moves to `docs/plans/completed/`; branch merges to `main`.
