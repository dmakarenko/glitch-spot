# Glitch Spot v0.4 — Coding Harness Design

**Date:** 2026-05-22  
**Stage:** v0.4-mcp  
**Initiative:** [`INITIATIVE.md`](./INITIATIVE.md)  
**Status:** Draft

---

## Goal

After saving a Glitch Spot annotation, the snapshot lands automatically in an active Claude Code session — with no copy-paste, no context switch, and CC staying fully responsive while it waits.

The developer types `/glitch-spot` once, annotates at their own pace, and CC either starts working (if the note is specific) or asks "what do you want me to do?" (if the note is vague).

---

## Two deliverables

1. **v0.4 MCP server additions** — what the Glitch Spot desktop app exposes  
2. **`/glitch-spot` CC skill** — how CC arms itself, waits, and consumes the snapshot

---

## 1. MCP server (Glitch Spot desktop app)

The MCP server runs inside the desktop app as a localhost HTTP server on a fixed port (default `7820`). It is already spec'd for `wait_for_snapshot`, `get_latest_snapshot`, and `get_snapshot`. This stage adds `cancel_wait`.

### Tools

| Tool | Signature | Behavior |
|---|---|---|
| `wait_for_snapshot` | `(timeout_seconds?: number)` | Blocks until the next snapshot is finalized. Returns full snapshot JSON. Default timeout: 600s, max 1800s. Only one waiter at a time; a second call replaces the first. |
| `get_latest_snapshot` | `()` | Returns the most recently finalized snapshot immediately. Returns `null` if no snapshots exist. |
| `get_snapshot` | `(id: string)` | Returns a specific snapshot by ID. Returns an error if not found. |
| `cancel_wait` | `()` | **New in v0.4.** Unblocks any in-flight `wait_for_snapshot` immediately. The blocked call returns `{ "cancelled": true }`. No-op if nothing is waiting. |

### Resources

- `glitch-spot://snapshots/latest` — same content as `get_latest_snapshot`
- `glitch-spot://snapshots/{id}` — same as `get_snapshot`

### Transport

Localhost HTTP. Standard MCP protocol over HTTP. Port `7820` (configurable via user settings in a later slice). The desktop app starts the server on launch and stops it on quit.

### One-time CC setup

The user registers Glitch Spot as an MCP server in `~/.claude/settings.json` once:

```json
{
  "mcpServers": {
    "glitch-spot": {
      "url": "http://localhost:7820/mcp"
    }
  }
}
```

After this, `wait_for_snapshot`, `get_latest_snapshot`, `get_snapshot`, and `cancel_wait` are available as native CC tool calls.

## 2. `/glitch-spot` CC skill

### The main loop

```
User: /glitch-spot
  ↓
Skill: health-check (get_latest_snapshot)
  ↓ [if Glitch Spot not running → emit setup error, stop]
  ↓ [if another waiter is already armed → emit conflict error, stop]
  ↓
Skill: record baseline snapshot ID
Skill: dispatch background Agent "glitch-spot-waiter" (run_in_background: true)
  │    Agent instruction: call wait_for_snapshot(timeout_seconds=600), return snapshot JSON
  ↓
Main session: "Ready. Go annotate — I'll be here."
  ↓
[Main CC session stays fully responsive — user can keep chatting]
[Background agent is waiting on the blocking MCP call]

  ← User hits hotkey, annotates, Cmd+Return →

Glitch Spot finalizes snapshot
  ↓
wait_for_snapshot() returns → background agent completes
  ↓
CC is auto-notified of background agent result (snapshot JSON)
  ↓
Skill reads annotated PNG via Read tool (CC sees image visually)
  ↓
Skill evaluates annotation notes:
  • Specific note ("fix this typo", "make this blue") → announce intent, start working
  • Vague note ("something's off") → show snapshot + ask "What would you like me to do?"
```

### States

**Arm state** (`/glitch-spot` invoked):

1. Call `get_latest_snapshot()` as a health check. If it throws a connection error, Glitch Spot isn't running — emit setup instructions and stop.
2. Check whether a background agent named `glitch-spot-waiter` is already running. If yes, tell the user and stop.
3. Record the current `latest.id` as baseline (or `null`).
4. Dispatch background agent `glitch-spot-waiter` with `run_in_background: true`.
5. Output: *"Ready. I'm watching for your next snapshot. Go annotate — I'll be here."*

**Present state** (background agent completes):

1. Receive result from agent. If result is `{ "cancelled": true }` — the user ran `/glitch-spot cancel` — do nothing (the cancel state already emitted feedback).
2. Read `~/.glitch-spot/snapshots/{id}/annotated.png` via `Read` tool. (If file missing, skip image, use text annotations only.)
3. Summarize annotations: "You marked N area(s): [list notes]."
4. Decide action:
   - Notes are specific and actionable → *"On it — [describe what I'm about to do]"* then start.
   - Notes are vague or missing → show image + *"What would you like me to do?"*

**Cancel state** (`/glitch-spot cancel`):

1. Call `cancel_wait()` on the Glitch Spot MCP server.
2. Background agent receives the cancelled sentinel and exits.
3. Output: *"Cancelled. Run /glitch-spot again when you're ready."*

### Error handling

| Condition | Behavior |
|---|---|
| Glitch Spot not reachable | "Glitch Spot isn't running. Launch the app and try again." |
| Waiter already active | "There's already a snapshot listener running. Snapshot `/glitch-spot cancel` first or wait for it." |
| Snapshot arrives, PNG missing | Present text annotations only; no image. Log: "annotated.png not found at expected path." |
| `wait_for_snapshot` times out (600s) | Background agent exits with timeout notice. CC surfaces: "Snapshot listener timed out. Run /glitch-spot to start again." |
| Discard modal chosen in Glitch Spot | Snapshot is never finalized → timeout fires. The cancel path above avoids the wait. |

## 3. Temporary fallback (pre-v0.4)

While v0.4 is not yet built, a simpler clipboard-based skill can provide the workflow at reduced fidelity:

1. `/glitch-spot` → *"When you're done annotating and have saved, come back and say 'got it'."*
2. User annotates, saves (JSON copied to clipboard by Glitch Spot)
3. User types "got it" → skill reads clipboard via `pbpaste`, parses the snapshot JSON
4. Skill reads annotated PNG from the path in the JSON (requires v0.3-persistence)
5. Presents and asks / acts

This requires one extra user action (coming back to say "got it") but needs no backend changes.

## 4. Snapshot presentation format

When surfacing a snapshot in CC, the skill formats it as:

```
[annotated.png shown via Read tool — CC sees it visually]

Snapshot snap_01HXYZ — 3 annotation(s):
  1. Rect [x:140, y:310, w:280, h:60] — "make this smaller and match the login button color"
  2. Rect [x:400, y:200, w:120, h:30] — "this text is clipped on small screens"
  3. Rect [x:60, y:500, w:200, h:80] — (no note)

Context: ProductDetailsPage — localhost:3000 — macOS 15.4
```

CC then decides: is annotation 1 specific enough to act on? Yes. Annotation 3 is vague (no note). In this case CC would ask about annotation 3 while acting on 1 and 2.

---

## 5. What this stage does NOT include

- Multi-session snapshots (one waiter per session, no fan-out to multiple CC instances)
- Remote relay / cross-machine handoff (v1.0)
- Web SDK DOM enrichment (v1.0)
- Stdin/stdio MCP transport (can add if a specific IDE needs it)
- LLM prompt synthesis / paraphrasing of annotations (cut decision — user notes are passed verbatim)

---

## Open questions

- **Port collision:** if port 7820 is taken, the app currently fails silently. Needs a graceful error + user-facing message (defer to packaging slice or v1.0).
- **Background agent naming:** CC's Agent tool doesn't yet have a "check if named agent is running" primitive. The skill may need to use a sentinel file (e.g., `~/.glitch-spot/.cc-waiter-active`) to track state across invocations.
- **Multiple CC sessions:** if two CC sessions both try to arm `wait_for_snapshot`, the second call replaces the first. This is a known limitation; fix in v1.0 if needed.
