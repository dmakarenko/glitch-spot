## 1. What this gives you

A teammate-shareable URL for any annotated snapshot, generated from the tray menu. The snapshot stays on your machine; only the URL travels. The teammate clicks the link in any browser (desktop, phone) and sees the annotated screen + a numbered list of notes.

---

## 2. How to use it

1. Trigger a snapshot with the existing hotkey (`Ctrl+Opt+Cmd+G` live, or `H` frozen). Drag rectangles, type notes, press `Cmd+Return`. (Unchanged from v0.2.)
2. Open the Glitch Spot tray menu → **"Share latest snapshot…"**.
   - First click of the session spawns the configured tunnel binary (default: cloudflared). Tray status briefly reads `Tunnel: starting…`.
   - On success, clipboard now contains a URL like `https://random-words.trycloudflare.com/share/snap_xxxxxxxxxxxx/<22-char-token>/` and a macOS notification fires.
3. Paste the URL to your teammate (Slack, email, etc.).
4. The URL works for the duration of the Glitch Spot session — quit the app and the URL goes dead.

**Repeat shares (same snapshot or new):** every click of "Share latest…" rotates the per-snapshot token; the previous URL stops working. The only durable share URL is the one currently on the clipboard.

**Tray status line** always shows one of:
- `Tunnel: idle`
- `Tunnel: starting…`
- `Tunnel: <host>` (e.g. `Tunnel: abc-def.trycloudflare.com`)
- `Tunnel: error — <reason>` (also fires a macOS notification on first entry into Error)

## 3. Provider setup (one-time prereqs)

The tray submenu **"Tunnel provider"** lets you pick cloudflared / ngrok / Tailscale Funnel. Choice persists to `~/.glitch-spot/config.toml`. Default is **cloudflared**.

### cloudflared (recommended — zero account)
```bash
brew install cloudflared
```
No further setup. Each share spawns `cloudflared tunnel --url http://127.0.0.1:7821` and grabs a fresh `*.trycloudflare.com` URL from its stderr.

### ngrok (free-tier account required)
```bash
brew install ngrok
ngrok config add-authtoken <your-token>
```
Each share spawns `ngrok http 7821 --log=stdout --log-format=json` and polls `http://127.0.0.1:4040/api/tunnels` for the public URL.

### Tailscale Funnel (zero new account if your tailnet already runs Tailscale)
Requires Funnel enabled for this device in the Tailscale admin console. Each share runs `tailscale funnel --bg 7821` and resolves the URL from `tailscale status --json` (`Self.DNSName`).

**Tailscale-specific note:** the `--bg` invocation is fire-and-forget. The Funnel persists in the `tailscaled` daemon even after Glitch Spot quits — unlike cloudflared/ngrok, the share URL does **not** automatically die on app quit. To revoke a Tailscale share, run `tailscale funnel reset` manually.

## 4. Architecture at a glance

```
glitch-spot process
├── MCP server      127.0.0.1:7820   (unchanged from v0.4)
│                                    POST /mcp — JSON-RPC tools for CC
│                                    ↑ stays private; not reachable through any tunnel
└── Share server    127.0.0.1:7821   (NEW)
                                     GET /healthz
                                     GET /share/{id}/{token}/             → HTML view
                                     GET /share/{id}/{token}/snapshot.json
                                     GET /share/{id}/{token}/clean.png
                                     GET /share/{id}/{token}/annotated.png
                                     ↑ this is what the tunnel exposes
```

The MCP control surface is on a separate listener and is never tunnelled. The share server is read-only (no POST/PUT/DELETE routes).

**Module map** (in `src-tauri/src/`):

| Path | Responsibility |
|---|---|
| `share/router.rs` | axum routes; constant-time token verify; serves files from `~/.glitch-spot/snapshots/{id}/` |
| `share/html.rs` | Pure `render_share_page(&Snapshot) → String`. HTML-escapes all user text. |
| `share/token.rs` | 128-bit OsRng tokens; atomic 0600 write via temp+rename; constant-time verify |
| `share/tunnel/mod.rs` | `TunnelManager` state machine: `Idle / Starting / Live / Error`. Owns the spawned binary (cloudflared/ngrok). Detects child early exit → transitions to `Error { reason: "tunnel disconnected" }` (skipped for Tailscale; see §3). |
| `share/tunnel/provider.rs` | `TunnelProvider` trait, `ProviderKind` enum, `ProviderError`. Trait method `child_persists_with_tunnel()` distinguishes long-lived children (cloudflared/ngrok) from marker children (Tailscale). |
| `share/tunnel/{cloudflared, ngrok, tailscale}.rs` | Per-provider spawn + URL discovery |
| `share/tunnel/log.rs` | Append-only tee to `~/.glitch-spot/tunnel.log` |
| `settings.rs` | `Settings::load_from(dir)` / `current_provider()` / `save_provider()` for `~/.glitch-spot/config.toml` |
| `lib.rs::run()` | Spawns both axum listeners at startup; `RunEvent::ExitRequested` calls `tunnel.shutdown()` (SIGKILLs the child) |
| `tray.rs` | Menu items + tunnel-state watcher (rebuilds menu on transitions; fires error notifications) |

## 5. Files on disk

```
~/.glitch-spot/
├── config.toml                              # [tunnel] provider = "cloudflared" | "ngrok" | "tailscale"
├── tunnel.log                                # append-only; all tunnel binary stdout/stderr lines tee'd here
└── snapshots/
    └── snap_<12-hex>/
        ├── clean.png                         # screen capture before annotations
        ├── annotated.png                     # screen capture with overlaid rects + notes
        ├── snapshot.json                     # full snapshot schema (see snapshot/mod.rs)
        └── share-token                       # ONLY present if user has shared this snapshot. mode 0600.
```

24h startup sweep (v0.3-persistence) deletes whole snapshot dirs older than 24h. `share-token` files go with them — there's no separate share-lifecycle.

## 7. Diagnosing problems

| Symptom | First place to look |
|---|---|
| "Tunnel: error — cloudflared not installed" | `which cloudflared` — install via brew |
| "Tunnel: error — <ngrok stderr>" | Run `ngrok http 7821` manually to see the full error; often "authtoken missing" |
| "Tunnel: error — Funnel disabled" (Tailscale) | Tailscale admin console → enable Funnel for the device |
| "Tunnel: error — <provider> didn't publish a URL within 10 s" | Network issue, or the provider is slow; check `~/.glitch-spot/tunnel.log` for the raw binary output |
| "Tunnel: error — tunnel disconnected" | The cloudflared/ngrok child crashed. Click "Share latest…" again to respawn. Check `tunnel.log`. |
| Recipient gets 404 on the URL | The Glitch Spot session that created the URL has quit. Re-share to get a new URL. |
| Recipient gets 404 even though Glitch Spot is running | Token rotated by a subsequent share. The clipboard URL is always the live one. |
| `127.0.0.1:7821` already bound | Another Glitch Spot instance is running. `lsof -i :7821` to find it. |

`~/.glitch-spot/tunnel.log` is the post-mortem tape. Every line from every tunnel adapter is prefixed `[cloudflared]` / `[ngrok]` / `[tailscale]`. Append-only; no rotation, so manually trim if it grows large.

## 8. Security posture (quick reference)

- **`/mcp` is never tunnelled.** It lives on a separate localhost-only listener (7820).
- **Share URLs need the token.** Snapshot ids alone are not enough — a snapshot without a `share-token` file 404s. Token is 128 bits, constant-time compared.
- **Token file is mode 0600**, written atomically via temp+rename so it's never world-readable, even briefly.
- **No data leaves the developer's machine via Glitch Spot.** The tunnel binary opens an outbound connection to its provider, which proxies incoming requests back to 127.0.0.1:7821 — Cloudflare/ngrok/Tailscale see only encrypted traffic between you and the recipient.
- **URL-as-secret model:** anyone with the URL can read the snapshot. Treat URLs accordingly (DM, not public channel).

## 9. Known limitations / future work

1. **No HTTPS pinning.** The recipient trusts whatever certificate cloudflared/ngrok/Tailscale provides. Fine for the threat model (no MITM concern between us and them), but means we can't promise specific TLS guarantees.
2. **Tailscale shares persist past app quit.** See §3. To revoke, run `tailscale funnel reset`.
3. **No share revocation UI.** To kill a URL while the app is running: re-share the same snapshot (rotates the token), or rely on the 24h snapshot sweep.
4. **No usage telemetry.** No idea how often this gets used or which providers work best. Wire up later if we want to optimize.
5. **Narrow race during shutdown-coinciding-with-disconnect.** If the tunnel child crashes within microseconds of the user quitting the app, a spurious "tunnel error" notification could fire. Documented in the regression-fix commit (`6440551`); not worth pursuing further unless seen in practice.
6. **No log rotation.** `~/.glitch-spot/tunnel.log` grows forever. Trim manually if it bothers you.

## 10. Where to pick up next

If you're an agent (or future-me) doing v1.1+ work in this area, useful starting points:

- **Add a fourth provider** (e.g., localtunnel, frp): implement `TunnelProvider` in a new file under `share/tunnel/`, add a `ProviderKind::*` variant, wire into the tray submenu.
- **Add HTML view polish** (mobile viewport meta, dark-mode CSS, copy buttons): `share/html.rs` is a pure function — easy to iterate with the `share::html::tests` golden assertions.
- **Add a "Share history" tray submenu** (last N share URLs): would need to keep an in-memory list of `(snap_id, token, timestamp)` in `TunnelManager` or a sibling struct. Not load-bearing.
- **Replace cloudflared `eprintln!` URL-extraction with the named-tunnel JSON API**: more robust but requires per-user setup.
- **Reach for the cloud relay (`later:` stage in INITIATIVE.md)** only if tunnel-based sharing proves insufficient (durable links across reboots, web-host DOM enrichment as a primary need).
